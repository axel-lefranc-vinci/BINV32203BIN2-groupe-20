Matrice de traçabilité des exigences

EF-32 — candidater et retirer sa candidature · EF-33 — consulter ses candidatures et leur statut. Une ligne est « couverte » uniquement si les assertions du test vérifient réellement le résultat attendu.

Méthode de lecture. Les tests ont été reliés aux cas précis du cahier des charges. Un simple appel HTTP sans assertion sur le résultat n'est pas considéré comme une couverture suffisante. Les chemins ci-dessous sont cliquables.

Comportements testés hors EF-32 / EF-33

Fonctionnalité contact d'entreprise

companies.test.ts vérifie que le contact peut lister et modifier les candidatures des offres de ses entreprises.

  • Liste 200 contenant les candidatures attendues.
  • Modification vers SELECTED réussie.
  • Contact d'une autre entreprise refusé avec 404 APPLICATION_NOT_FOUND.

Données de démonstration

Le seed fournit des cas utiles pour les essais manuels : deux candidatures en cours, une candidature retenue, une non retenue et une retirée.

Ces données ne remplacent pas une assertion de test : elles permettent surtout de reproduire les parcours dans l'interface.

Manques identifiés et traitement

Manques conservés

  • Ajouter un test dédié au retrait d'une candidature REJECTED.
  • Vérifier explicitement le titre et le nom de l'entreprise dans la réponse EF-33.
  • Vérifier explicitement le statut REJECTED via GET /applications/mine.
  • Ajouter un test de refus de GET /applications/mine pour un contact.

Pourquoi ces cas restent des limites

Ils ne bloquent pas les règles principales déjà vérifiées, mais leur absence empêche de déclarer une couverture complète de tous les statuts et de tous les profils. Aucun test end-to-end navigateur n'est présent ; la validation UI reste manuelle.

Les tests ajoutés dans offers.test.ts feraient échouer la suite si l'API acceptait un doublon actif ou convertissait silencieusement un offerId invalide.
