Gesta · architecture applicative

Afficher les offres de stage

Parcours complet, du composant React jusqu'aux lignes SQLite, avec le périmètre d'un futur filtre par période.

1. Vue d'ensemble

L'application est un monorepo npm composé d'un frontend React/Vite et d'une API Express/TypeScript. Le frontend appelle /api/offers. Le proxy Vite retire /api et transmet la requête à l'API (par défaut sur le port 3000). Le backend est organisé en contrôleur, service, repository et mapper, puis lit SQLite avec better-sqlite3.

1 · Route ReactApp.tsx rend OffersPage pour /offres.
2 · PageOffersPage.tsx utilise useOffers et choisit l'état à afficher.
3 · HookuseOffers.ts déclenche le chargement et gère chargement, erreur, annulation et 401.
4 · HTTPoffers.service.ts appelle GET /api/offers et valide le JSON.
5 · APIAuthentification, autorisation, contrôleur, service et repository filtrent puis chargent les offres.
6 · UIOfferTable.tsx affiche le DTO : titre, entreprise, année, période et statut.

2. Parcours frontend

  1. Entrée et accès à la page. Dans frontend/src/App.tsx, useAuth fournit l'utilisateur, le jeton et la déconnexion. La route /offres n'est montée que si canListOffers(user) est vrai. La page reçoit le jeton et onUnauthorized.
  2. Chargement. Dans frontend/src/pages/OffersPage.tsx, useOffers(token, onUnauthorized) est appelé. La page affiche un chargement, une erreur, un état vide, ou le nombre de résultats suivi de OfferTable.
  3. Hook et cycle de vie. Dans frontend/src/hooks/useOffers.ts, un useEffect crée un AbortController et appelle getOffers. Le nettoyage annule la requête précédente. Une réponse 401 appelle onUnauthorized; les autres erreurs sont conservées pour ErrorState.
  4. Service et validation. Dans frontend/src/services/offers.service.ts, fetch envoie le jeton directement dans l'en-tête Authorization, sans préfixe Bearer. La fonction readJson vérifie le statut puis isOfferList valide les champs et les codes de période/statut.
  5. Rendu. Dans frontend/src/components/OfferTable.tsx, chaque offre devient une ligne. Le code de période est transformé en libellé français par PERIOD_LABELS; le statut passe par StatusBadge.

3. Parcours backend et base de données

  1. Route Express. Dans backend/src/app.ts, /offers est branché derrière authenticate. Le contrôleur est créé par createOffersRouter.
  2. Authentification et droits. Dans authenticate.ts, le jeton identifie l'utilisateur, puis ses données, rôles et rattachements sont relus en base. Dans authorize.ts, canListOffers autorise les administrateurs, étudiants et contacts ayant le rôle DEPOSITOR. Les autres contacts reçoivent 403.
  3. Contrôleur. Dans offers.controller.ts, GET /offers appelle le service avec l'utilisateur courant puis convertit chaque résultat avec toOfferDto.
  4. Règle de visibilité. Dans offers.service.ts, visibilityFilter produit le filtre métier : toutes les offres pour l'administrateur, seulement PUBLISHED pour l'étudiant, et les offres déposées par le contact pour un déposant.
  5. SQL et jointures. Dans offers.repository.ts, le repository joint offers à companies, academic_years et periods. Il trie par date de début d'année décroissante puis par date de création décroissante. Il renvoie un OfferDbo, transformé ensuite en objet métier puis en DTO.
  6. Schéma. Dans 001_initial.sql, offers.period_id référence periods.id et offers.academic_year_id référence l'année correspondante via une clé étrangère composite. Une période porte un code (P1, P2 ou OTHER) et appartient à une année académique.

4. Fichiers concernés par un filtre par période

Le choix recommandé est un filtre côté serveur : il conserve les règles de visibilité du backend et évite de télécharger des offres inutiles. Le paramètre pourrait être, par exemple, GET /offers?period=P1. Il doit être validé contre les codes déjà définis, sans modifier le schéma puisque la période existe déjà dans la base.

À préserver pendant l'ajout : le filtre de période est une restriction supplémentaire, jamais un remplacement du filtre de visibilité. Un étudiant ne doit toujours recevoir que des offres publiées et un déposant uniquement ses propres offres, même s'il fournit une période valide.
